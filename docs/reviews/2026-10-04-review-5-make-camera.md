### 2.5 ショット間の 1 フレームのカットと補間: 30 fps では問題なし。60 fps は要確認（低）

- 各ショットの終点キー（end）と次の始点キー（end+1）が 1 フレーム差。vmd のキーの曲線は「前のキーからそのキーまで」
  に効く（一般に知られた仕様。下請けも未実測と明記）ので、1 フレーム区間に効くのは次ショットの始点キーの S 字。
  30 fps で描く限りフレームは整数で、end と end+1 の間に描かれるフレームは無い。中間の絵は出ない。
- 60 fps で書き出す（`render avi --fps 60`）と end+0.5 が描かれる。S 字 (64, 0, 64, 127) は x = 0.5 で y = 0.494
  （線形 0.5 とほぼ同じ）なので、カットの中間の絵が 1 枚（1/60 秒）混じる。MMD が 1 フレーム差のカメラキーを
  補間しない特別扱いをする、という挙動を記憶しているが**未実測（推測）**。確かめるなら hinata で --fps 60 の抜粋。
  避けるには始点キーの曲線を (127, 0, 127, 0)（x = 0.5 で y = 0.009、ほぼ段差）にする。
- 今の MV の台本（`hinata_camera_variants_D.txt`）は 30 fps なので実害なし。

## 3. 強さの解析

### 3.1 四元数の角度差・疎なキー・同フレームの重複・窓の端: 問題なし

- `quat_angle`: 両方のノルムで割り、`abs(dot)` を 1 で clamp して `2 acos`。ノルム 0 なら 0。下限は abs で保証される
  ので `acos` の定義域は守られる。q と −q が 0 になる試験あり。
- 同じフレームに同名ボーンのキーが 2 本ある vmd（実物に 2 組ある）: `span <= 0` の対で飛ばす。その 2 本の間の変化は
  数えない（同フレームなので画面上は瞬間。妥当）。落ちない。
- 疎なキー（全ての親 1 キー・グルーブ 2 キー・下半身 25 キー）: 対が無ければ 0、長い区間は一定の低い率に薄まる
  （直線移動の仮定どおり）。
- 30 フレーム窓 [f−15, f+15) は端で縮んだ分を 30/実幅 で揃える。フレーム 0 は変化を持たない（変化は (a, b] に置く）ので
  先頭 15 フレームだけ 28/30 程度に沈むが、無視できる。
- 区切りの強さ（前後 90 フレームの trend の平均差）は f ≧ 1 なので空のスライスにならない。

### 3.2 重み: 名前の部分一致の順序は意図どおり。腕捩と半角 IK だけ注意（低）

- 先勝ちの順で 手首 1.5・足首 1.0 が 首 3.0 より先、ＩＫ 1.0 が 足 8.0 より先、指 0.5・目 0.2 が最初。
  「右手捩」（実物で 1,297 キー）はどれにも当たらず既定 1.0、「右腕捩」は 腕 7.0。捩り（軸まわりの回転）は末端を
  ほとんど動かさないので 7 は過大。`("捩", 1.0)` を 腕 より前に置けば直る。
- ＩＫ は全角だけ。英語名・改造モデルの半角 "IK" は 足 8.0 に落ちる（実物は全角なので今回は無関係）。`("IK", 1.0)` を足す。
- 重みが「末端の長さの近似で実測なし」なのは記録どおり。合成ダンスで 腕 > ひじ > 頭 > 指 の順序は試験が守る。

### 3.3 閾値の決め方の頑健さ

- 依頼文の「中央値・p10・p90」ではなく trend の p35 / p65 + ヒステリシスを採っている（記録 1 に理由。拍で反転しない
  ため）。短い vmd（200 フレーム、2 キー、last = 1）・骨 0 本・フレーム 0 だけ、を流して: 骨 0 本と 0 だけは ValueError
  （終了コード 2）、他は落ちずに 1 ショット。
- 遅れ（2.2）と平坦な入力の扱い（2.6 の低）は上に書いた。

## 4. 決定性と再現性: 問題なし

- `random.Random(seed).random()` 1 回の重みつき抽選。`random.choices` を使っていないので版に依らない。
- 辞書順序: `tracks_of` はファイル順、`strength` は区切りのフレーム順、`clear` は sorted、同点は早いフレーム。
  集合（set）は実装では使っていない。ハッシュ順への依存なし。
- 浮動小数: JSON は `_r` で小数 4 桁に丸める（`+ 0.0` で −0.0 を消す）。vmd は丸めずに float32 で書く。
  同じ入力・同じ seed で同じバイト列（試験あり。実物でも委ねられたファイルと同一を確認）。
- 骨の並びが違う同内容の vmd（保存し直したもの）では加算順が変わり最終桁が揺れうるが、「同じ入力」の定義の外。

## 5. 書き出し

### 5.1 `for_camera`・曲線・`.part`・読み戻し: 問題なし

- `vmd.Motion.for_camera(cameras=...)` でモデル名「カメラ・照明」、骨 0・表情 0・照明 0・影 0。照明キー 0 本の
  カメラ vmd は配布カメラ（260 キー、照明 0・影 0）と同じ形で、MMD が読む形。
- 曲線: 全キー・全 6 チャンネルが (64, 0, 64, 127)（生成物 42 キーで確認）。`camera_interpolation` のバイト並びは
  x1 x2 y1 y2 で、`camera_curves` で往復する。docstring の「配布カメラも使う曲線」は、配布カメラの 1,560 チャンネル
  曲線のうち 24 がこれ（1,501 は線形 (20, 20, 107, 107)）。嘘ではないが「配布カメラは大半が線形」が実態。
- `write_bytes`: `.part` に書いて `os.replace`、`finally` で `.part` を消す。フォルダは作る。出来た vmd を
  `vmd.load` で読み戻してキー数と両端のフレームを返す（規則どおり）。`mmd motion keys` で読めた
  （`kind: camera`、`cameras: 42`、`ranges [0, 7742]`、`--camera --from 0 --to 1400` で 9 キーの表示値が報告と一致）。

### 5.2 入力と出力に同じパスを渡すと入力のダンスが消える（中）

- 場所: `run()`。`dance_full` と `out_full` を比べていない。
- 何が起きるか: `vmd.load(dance)` → 計画 → `write_bytes(out)` が同じファイルを置き換える。`.part` → `os.replace`
  なので元のダンスは戻らない（`motion edit` の `.mmdcli-old` 退避も使っていない）。打ち間違い 1 回で配布モーションを
  失う。
- 直し方: `os.path.normcase(dance_full) == os.path.normcase(out_full)` なら ValueError（「OUT は DANCE と別のファイルに」）。
  試験 `test_dance_and_out_must_differ`。
- 重要度: 中（起きにくいが、起きたら戻らない）。

### 5.3 低いもの

- vmd を書いた後に `--report` / `--analysis` の書き込みで失敗すると、vmd は残るのに `{"ok": false}` で終了 2。
  先に 3 つの出力先が書けるか確かめるか、結果に「vmd は書けた」と出す。
- 既存の OUT は黙って置き換える（試験で保証）。`motion edit` と違い退避を作らない。記録 3 に理由あり（app は Windows
  依存の import を抱える）。取り込み後に規則を揃えるなら `keeping_the_old_file` だけを別モジュールへ出す手がある。
- 出力先がフォルダなら OSError（Windows は PermissionError）の生の文言。`motion edit` は「フォルダです」と言う。
