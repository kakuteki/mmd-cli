## 1. 正しさの欠陥（ctypes、資源、競合、例外、タイムアウト）

### 1.1 ctypes の宣言（実測。問題なし）

win32.py の構造体を Windows SDK の定義（x64）と突き合わせた。スクリプトで `ctypes.sizeof` と各欄の offset を比較した結果:

| 構造体 | win32.py | SDK | 判定 |
| --- | --- | --- | --- |
| INPUT (`_INPUT`) | 40 | 40 | 一致。`type` offset 0、共用体 offset 8、`ki.wVk` offset 8、`mi.dwFlags` offset 20 |
| MOUSEINPUT | 32 | 32 | 一致（全欄の offset 一致） |
| KEYBDINPUT | 24 | 24 | 一致（同上） |
| STARTUPINFOW | 104 | 104 | 一致（同上） |
| PROCESS_INFORMATION | 24 | 24 | 一致（同上） |
| DROPFILES（`make_drop_handle` が pack する 20 バイト） | 20 | 20 | 一致。`pFiles=20`、`fWide=1`、末尾は UTF-16 の二重 NUL |

`_INPUT` の共用体に HARDWAREINPUT（8 バイト）が無いが、MOUSEINPUT の方が大きいので大きさ・配置に影響しない。
以前の SendInput の失敗（INPUT の大きさ違い）は、現在の版では直っている。

argtypes / restype も確認した。

- `SendMessageTimeoutW`: `lpdwResult` を `POINTER(c_size_t)`（= PDWORD_PTR）、restype `c_ssize_t`（= LRESULT）。正しい。
- `PostMessageW` / `SendMessageTimeoutW` の lParam を `c_void_p` にしている。`c_void_p.from_param` が
  `create_unicode_buffer` の配列を受け付けることを実測した（受理）。int も None も通る。正しい。
- `GetWindowLongW` restype `c_long`、`SetWindowLongW` 第 3 引数 `c_long`: 拡張スタイルの値は 32 bit に収まるので可。
  `c_long.from_param(0xFFFFFFFF)` は例外にならず黙って -1 に切り詰めることを実測した。bit 31 を使う
  拡張スタイルは無いので今は害が無いが、`style()` / `ex_style()` が `& 0xFFFFFFFF` で正に直しているのに
  `hide_window` / `reveal_window` は生の負値のまま OR している。統一しておくとよい（重要度 低）。
- `GetWindowThreadProcessId` の第 2 引数 `POINTER(DWORD)`、`GetClassNameW` の `LPWSTR`、`EnumWindows` の
  コールバック型 `WINFUNCTYPE(BOOL, HWND, LPARAM)`、`GlobalAlloc`/`GlobalLock` の `c_void_p`、
  `OpenProcess`/`WaitForSingleObject`/`CloseHandle`/`TerminateProcess`、`CreateProcessW`（`lpCommandLine` を
  書込可能なバッファで渡している）: いずれも正しい。
- `SetLayeredWindowAttributes(HWND, DWORD, c_ubyte, DWORD)`、`GetLayeredWindowAttributes` の 3 つのポインタ: 正しい。
- `SetThreadDpiAwarenessContext(c_void_p(-1))` = DPI_AWARENESS_CONTEXT_UNAWARE: 正しい。これは呼んだスレッドにしか
  効かないが、座標を扱う `window_rect` / `SetWindowPos` / `is_hidden` は主スレッドだけで呼ばれ、見張りスレッド
  （FocusShield）とワーカースレッドは座標を使わない。実測ではこの PC の python.exe は新しいスレッドでも
  awareness 0（unaware）だった。問題なし。
- argtypes 未宣言のまま呼んでいる関数: `AllowSetForegroundWindow`、`LockSetForegroundWindow`、
  `GetCurrentProcessId`、`timeBeginPeriod`/`timeEndPeriod`（win32.py:266-277, 507-514）。引数はすべて 32 bit に
  収まる int なので現状は正しく動く。restype が既定の c_int なので PID が 2^31 を超えると負になるが実害は無い。
  宣言だけ足しておくのが安全（重要度 低）。
- `wt.WPARAM` は x64 で `c_ulonglong`（実測）。`make_drop_handle` が返す 64 bit のハンドルを wParam に渡しても欠けない。

### 1.2 WM_DROPFILES の HDROP の寿命（実測。問題なし）

場所: win32.py:430-441 `make_drop_handle`、app.py:253-255 `Mmd.drop`。

GlobalAlloc したブロックを誰が解放するかを、pythonw.exe のメッセージ専用窓（画面には何も出ない）を受け手にして測った。

| 経路 | 受け手 | 送り手のハンドル（PostMessage の直後） |
| --- | --- | --- |
| PostMessage | 正しいパスを読めた（DragQueryFileW）。受け手側のブロック大きさは送った大きさと同じ | `GlobalSize` が 0、`GlobalFlags` が 0x8000（GMEM_INVALID_HANDLE）= システムが投函時に所有権を取り、送り手側では無効になる |
| PostMessage の直後に送り手がバッファを書き換える試み | 元のパスを読めた | `GlobalLock` が NULL（既に無効） |
| PostMessage の直後に `GlobalFree` | 元のパスを読めた | `GlobalFree` は失敗を返す（既に無効なので害は無いが無意味） |
| SendMessageTimeout | ハンドルが読めない（DragQueryFileW が 0、GetLastError 6） | ブロックは送り手に残る（解放されない） |

結論: 現在の実装（投函し、送り手は解放しない）は正しい。送り手で `GlobalFree` を足す必要は無いし、足しても無効ハンドルへの呼び出しになるだけである。
spike-result の「投函の経路でだけハンドルが相手側へ写される」は正確で、より正確には「投函時に所有権が移る」。
受け手側（MMD）の写しは MMD の `DragFinish` が解放する。送り手にリークは無い。

### 1.4 relay: 子の `.exit` が原子的に書かれず、親が空のファイルを読んで終了コード 0 にする

場所: relay.py:236-237（`run_job` の `.exit` 書き出し）と relay.py:205-210 + 136-148（親の待ちと `collect`）。

何が起きるか: 親は `.exit` が「存在する」ことだけを待って即座に読む。子は `open(..., "w")` でファイルを作ってから
`write(str(code))` するので、作成と書込の間に親が読むと空文字列を読み、`collect` は `int("" or 0)` で 0 を返す。
失敗した命令（本来 1 や 3）が終了コード 0 で返る。JSON 本文は `ok: false` のままなので、終了コードだけを見る
呼び出し側（CI、`&&` 連結）が成功と誤認する。

根拠: コードの読み取り。窓は数十マイクロ秒で、親の監視間隔は 100 ms なので頻度は低いが、ゼロではない。
`.out.json` 側は `emit` が `.part` → `os.replace` で原子的に書いているので同じ問題は無い（cli.py:27-31）。

直し方: 子は `.exit.part` に書いて `os.replace` する。親は `collect` で空を読んだら 1 回待ち直す。
さらに、`.exit` の中身に exit code と一緒に `.out.json` の大きさを書いて照合すると取り違えが無くなる。

重要度: 中（頻度は低いが、起きると失敗が成功に化ける）。

### 1.5 relay: 親の待ち時間が子の実際の待ち時間より短く、AVI の中継は 180 秒で必ず失敗する

場所: cli.py:528（`timeout=(args.timeout or 120.0) + 60.0`）、app.py:942-943（子は `max(120, 60 + 2 * フレーム数)`）、
relay.py:205-217。

何が起きるか: SSH 越しに `mmd render avi out.avi --from 0 --to 300` を実行すると、子は最大 662 秒待つ設計だが、親は
180 秒で `RelayError` を返し、`finally` でタスクと `.json` / `.out.json` / `.started` を消す。子はそのまま
書き出しを続け、終わると消された場所に `.out.json` と `.exit` を作り直す（誰も回収しないごみ）。利用者には
「did not finish within 180 s」が返り、実際には数分後に AVI が出来上がる。`--timeout` を自分で大きく指定しない限り
中継経由の AVI は 60 フレーム以上で成功しない。

根拠: コードの読み取り。両者が別々の式で待ち時間を決めている。

直し方: 親の待ち時間を子と同じ規則で決める（`render avi` のときは `60 + 2 * フレーム数` を加える）か、
もっと確実には、親は `.started` に書かれた子の PID が生きている限り待ち続け（`process_alive`）、
子が死んでいて `.exit` が無いときだけ失敗にする。親が諦めるときは `schtasks /End` で子を止めてから掃除する。

重要度: 高。

### 1.6 relay: 中継の要否を「最初の位置引数」で決めるので、値つきの共通オプションが前にあると誤判定する

場所: relay.py:58-59。

何が起きるか: `positional = [a for a in argv if not a.startswith("-")]` は `--out r.json` の `r.json` や
`--timeout 30` の `30` も位置引数として数える。`mmd --out r.json file info x.vmd` を SSH から実行すると
`positional[0]` は `r.json` なので `file` が LOCAL_COMMANDS に当たらず中継される。誰もログオンしていない機では、
MMD の要らない `file info` が「is anyone logged on」のエラーになる。実測（should_relay を直接呼んだ）:
`--out r.json file info x.pmm` → True、`--timeout 9 file info x.pmm` → True、`file info x.pmm` → False。

直し方: `main` は既に `args` を持っているので、`should_relay(argv, command=args.command)` のように解析済みの
コマンド名を渡して判定する。

重要度: 中。

### 1.7 relay: 子が中継を再び起こす歯止めが無い

場所: relay.py:78-102 `child_argv`、relay.py:220-238 `run_job`。

何が起きるか: 子の argv からは `--in-user-session` も `--no-relay` も取り除かれる。子が万一 WinSta0 以外
（タスクが対話セッションで始まらなかった場合）で動くと、子の `main` → `should_relay` が True になり、
子がさらにタスクを登録して孫を待つ。各段が 15 秒 / 180 秒待つ連鎖になる。`/IT` が守られている限り起きないが、
守りが一段しかない。

直し方: 子の argv に `--no-relay` を足す（または環境変数 `MMD_CLI_RELAYED=1` を job に入れ、`should_relay` で見る）。

重要度: 低。

### 1.8 relay: 後始末の抜け

場所: cli.py:520-527（`batch -` の stdin を `relay/stdin-<pid>.txt` に退避）、relay.py:211-217。

何が起きるか: 退避した stdin ファイルは誰も消さない。1.5 の経路では子が後から `.out.json` / `.exit` を作り直す。
`relay/` にごみが溜まる。

直し方: 親の `finally` で退避ファイルも消す。子は書く前に job ファイルの存在を確かめ、無ければ（親が諦めた）結果を書かない。

重要度: 低。

### 1.9 state.json の同時書き込み

場所: app.py:54-59 `save_state`、app.py:43-51 `load_state`。

何が起きるか: 一時ファイル名が固定（`state.json.tmp`）で、読み・変更・書きの間に錠が無い。2 つの `mmd` プロセスが
同時に `save_state` を呼ぶと（例: 2 体の MMD を 2 つのエージェントが別々に動かす、`mmd launch` と `mmd quit` の
同時実行）、片方の `open(tmp, "w")` と他方の `os.replace(tmp, ...)` が重なって PermissionError / FileNotFoundError で
落ちるか、後勝ちで `current` や `projects` の更新が消える（例: 一方の `launch` が設定した `current` が、
他方の古い状態の書き戻しで上書きされる）。README は「1 つの MMD に同時に 2 つのコマンドを走らせない」と書くが、
state.json は MMD をまたいで 1 つなので、別インスタンス同士でも衝突する。

根拠: コードの読み取り。

直し方: 一時ファイル名に PID を入れる（`state.json.<pid>.tmp`）、`os.replace` を数回まで再試行する、
`projects` の更新は読み直してから当該 PID の項目だけ差し替える。

重要度: 中。

### 1.10 guard: ワーカースレッドと見張りの競合、例外で飛ぶ後始末（見たが大きな問題なし）

- `Guard.run` の "send" モード（guard.py:150-156, 199-200）: ワーカーは `SendMessageTimeout` に `timeout + 5 s` を
  渡しているので、主ループが先に `DialogPending` / `OperationTimeout` を投げても、ワーカーはその後 MMD が
  ダイアログを閉じるまで（または待ち時間まで）ブロックしたまま残る。CLI はプロセスごと終わるので無害。
  batch（1 プロセスで多数の命令）では、後から `dialog click` で答えれば SendMessage が戻って終わる。実害は無いが、
  ワーカーが生きている間に次の命令の `send` を重ねることになる点は意識しておく（重要度 低）。
- `with FocusShield(self.pid), win32.timer_resolution()`（guard.py:167）: 例外でも両方の `__exit__` が走る。
  `FocusShield.__exit__` は見張りスレッドを止めてから `LockSetForegroundWindow` を解除する。入れ子は外側だけが
  実体になる。正しい。
- `FocusShield._outer` はクラス属性で、プロセス内で 1 本と決め打ちしている。batch の `shield.pid = ...` の書き換えは
  見張りスレッドと同時に読まれるが、int の代入なので壊れない。
- `_press` / `_press_yes`（app.py:274-282, 734-740）がハンドラの中から `DialogPending([dialog])` を投げると、
  `Guard.run` がそれまでに集めた `events`（同じ実行で自動応答したダイアログ）はこの例外に載らず、
  `Mmd._run` の `self._keep(exc.events)` にも渡らない。失敗時の `answered_dialogs` が欠ける（重要度 低。
  1.12 と合わせて直す）。
- `Guard.run` のハンドラが例外（TypeError など）を投げた場合、ダイアログは隠したまま残り、CLI は終了コード 1 で
  その例外を報告する。次の命令で `DialogPending` になるので詰みはしないが、下の 1.11 参照。

### 1.11 ダイアログの中身を決め打ちするハンドラが `None["hwnd"]` で落ちる

場所: app.py:878-882 `output_size.on_size`、887-894 `set_output_size.on_size`、947-948 `put`、950-951 `on_settings`、
781-782 `render_codecs.on_settings`。

何が起きるか: `dialog.find_control(ID, "Edit")` が None を返す状況（English Mode の MMD、別版の MMD、同じ題名の
別のダイアログ）で `None["hwnd"]` が TypeError になる。利用者には「'NoneType' object is not subscriptable」が
終了コード 1 で返り、ダイアログは隠れたまま残る（次の命令で初めて `DialogPending` になる）。
`_fill_file_dialog`（app.py:261-265）だけはコントロールが無ければ `False` を返して再試行する形になっているので、
同じ形に揃えるとよい。

根拠: コードの読み取り。v9.32 日本語表示では起きない。

直し方: コントロールが揃っていなければ `return False`（再試行）、`SETTLE_SECONDS` を過ぎたら `DialogPending` にする
共通の小関数を作る。

重要度: 低。

### 1.12 失敗した命令では自動応答したダイアログの記録が捨てられる

場所: cli.py:352-360 `run`、cli.py:535-538 `main`。

何が起きるか: `finally: answered = mmd.take_events()` で取り出すが、例外経路では `result` が無く `failure(exc)` の
JSON にも入れないので、失敗した命令の途中で自動的に押したボタン（例: `_press_yes` が押した「はい」、
`model_info` の OK）が利用者から見えない。何かを黙って押したうえで失敗した、という最も知りたい情報が落ちる。

直し方: `failure()` に `answered` を渡して `error["answered_dialogs"]` に入れる。`DialogPending.events` も同様に出す。

重要度: 中。

### 1.13 `play --wait --repeat` は再生を始めてからエラーにする

場所: app.py:1000-1005。

何が起きるか: `--repeat` と `--wait` の矛盾は再生ボタンを押して `playing` になった後に `ValueError` にしている。
エラーが返った時点で MMD は繰り返し再生中になり、以後の命令は `mmd stop` まで全部拒否される。

直し方: 引数の検査（`if wait and repeat: raise`）を `require_ready()` の直後に移す。

重要度: 中。

### 1.14 `launch` がダイアログで失敗すると、隠したダイアログつきの MMD が残り、答える手段が無い

場所: app.py:121-125。

何が起きるか: 起動途中のダイアログ（例: `Direct3D::Init` の `CreateDevice Failed!`）を `open_dialogs(hide=True)` で
透明化してから `DialogPending` を投げる。主窓がまだ無い段階だと、`Mmd.attach` は「MMD is not running」で失敗し、
`--pid` でも「no MMD window belongs to pid」になるので、`mmd dialog click` / `dialog show` が使えない。
利用者から見えない透明なダイアログを持った MMD プロセスが残り、タスクマネージャでしか止められない。
`state["current"]` も書かれない。

直し方: `launch` の失敗経路では、ダイアログを `reveal_window` で見える状態に戻すか、プロセスを `terminate_process` で
終わらせてから例外にする。少なくとも例外文に PID を入れる。

重要度: 中（起きるのは環境依存の初期化失敗だけだが、起きたときの詰み方が悪い）。

### 1.15 作業用ディレクトリのパスが cp932 で表せるか確かめていない

場所: app.py:30-36 `home_dir`、284-287 `_temp_path`、514-517 `_new_work_path`、relay.py:117-120。

何が起きるか: 入力・出力のパスは `_require_ansi` で検査するが、`%LOCALAPPDATA%/mmd-cli` 配下（利用者名を含む）と
`MMD_CLI_HOME` は検査しない。利用者名に cp932 に無い文字（ハングル、簡体字、絵文字など）があると、
`bone set` / `morph set` / `pose load --register` が作る vmd と、`dump` / `save` の作業用 pmm のパスが MMD に届かず、
「MMD did not register a key」「MMD did not write ...」という原因の分からないエラーになる。

直し方: `home_dir()` で `_require_ansi` を掛け、だめなら「MMD_CLI_HOME を cp932 で表せる場所に設定せよ」と
言う。relay の `relay_dir` も同じ。

### 1.17 新しく入った `owner_window` が argtypes / restype 無しで `GetWindow` を呼ぶ（INPUT と同じ種類の誤り）

場所: win32.py:411-412（9e2d2d97 版）`return user32.GetWindow(hwnd, 4)`。呼び出し元は app.py:280 `_file_handlers.on_message`。

何が起きるか: argtypes が無いので `hwnd` は C の `int`（32 bit）として渡される。Python 側の hwnd は `wt.HWND`
（c_void_p）の戻り値で、値の bit 31 が立っていると符号拡張された 64 bit の大きな正の整数になり、宣言無しの呼び出しは
`ctypes.ArgumentError: int too long to convert` で落ちる（1.1 の実測スクリプトで、同じ条件の `GlobalSize(h)` が
この例外になった）。restype も既定の c_int なので、返る所有者の HWND は 32 bit に切り詰められる（USER ハンドルは
32 bit を符号拡張した値なので、これは結果的に正しい値になるが、宣言で保証されていない）。現在の Windows では
HWND の上位 16 bit は小さな連番で bit 31 が立つことは稀なので、実機では動いて見える。

直し方: `user32.GetWindow.argtypes = [wt.HWND, wt.UINT]`、`user32.GetWindow.restype = wt.HWND`。
5.1 の `test_every_declared_function_has_argtypes` を入れておけば、この種の追加漏れは単体試験で止まる。

重要度: 低（今は動くが、INPUT の件と同じく宣言漏れで、見つけにくい形で壊れる）。

## 2. 窓メッセージの前提

- PostMessage / SendMessage の使い分け: 同期で結果を待ちたい `WM_COMMAND` は別スレッドから `SendMessageTimeout`、
  相手がモーダルループに入る可能性のあるものは主スレッドを塞がない。`WM_DROPFILES` と Enter は投函。
  1.2 の実測で、`WM_DROPFILES` は投函でなければならないことが裏付けられた（SendMessage では受け手が読めない）。正しい。
- 別プロセスへの `WM_SETTEXT` / `WM_GETTEXT` / `CB_GETLBTEXT` / `LB_GETTEXT`: これらはシステムがバッファを
  相手プロセスへ複写するメッセージなので、`create_unicode_buffer` を lParam に渡す今の形で正しい。
  `get_text` は `WM_GETTEXTLENGTH` の長さ + 2 文字のバッファを用意し、`WM_GETTEXT` の wParam に長さ + 1 を渡す。正しい。
- `CB_SETCURSEL` は通知を出さないので `CBN_SELCHANGE` を自分で送る（app.py:242-245）。正しい。
- `BM_CLICK` を投函する `play` / `stop`（app.py:1000-1001, 1013）: 再生ボタンの押下は MMD 側で再生ループに入るので
  同期で送らないのが正しい。`_wait_for(self.playing)` で確かめている。
- HDROP の寿命: 1.2 参照。送り手は解放しない（してはいけない）。
- `WS_EX_NOACTIVATE` と `LockSetForegroundWindow`: spike の実測どおり。`FocusShield` の `_check` は MMD のプロセスの
  窓が前面になったときだけ戻す。`give_foreground_back` の「長さ 0 のマウス移動を SendInput してから
  SetForegroundWindow」は、自分を最後の入力プロセスにする定石で、INPUT の大きさも正しいことを確認した（1.1）。
- 見張りの対象クラスは `#32770` と `RecWindow` だけ（guard.py:13）。MMD が他のクラスの最上位窓を開く操作
  （MME の設定窓など）は見張られない。README に MME 未確認と書いてあるので、そのままでよい。

## 3. ファイル形式（vmd / vpd / pmm）の境界条件

実測した結果（スクリプトで `loads` / `dumps` に直接入力）を先に表にする。

| 入力 | 結果 | 判定 |
| --- | --- | --- |
| vmd: 空、magic だけ、ヘッダ 50 バイトで件数なし | ValueError（bad magic / header is truncated） | 良い |
| vmd: 件数 0 の最小ファイル（54 バイト） | 空の Motion | 良い |
| vmd: ボーン件数 0xFFFFFFFF でデータなし | 即座に ValueError（offset 54）。`range(4e9)` を回り切らない | 良い |
| vmd: 20 万キー（22 MB） | 0.94 秒で読める | 可（3.4） |
| vmd: 名前欄の NUL の後ろにごみ | NUL で切れる | 良い |
| vmd: 名前がちょうど 15 バイト | 受理 | 良い |
| vmd: 名前が cp932 に無い文字（U+2665 など） | `UnicodeEncodeError` が生で出る | 3.1 |
| vmd: pmm から 'replace' で読んだ U+FFFD を含むモデル名 | `_truncated` が `UnicodeEncodeError` | 3.2 |
| vmd: 負のフレーム | `struct.error` が生で出る | 3.1 |
| vmd: NaN の重み | そのまま書ける | 3.5 |
| vpd: 空 | ValueError | 良い |
| vpd: ヘッダだけ、LF 改行だけ、名前に `}`、指数表記、コメント中の `Bone0{` | いずれも正しく読む | 良い |
| vpd: 親ファイル名に "Bone" を含む（MyBone.osm） | `model_file` が空になる | 3.3 |
| vpd: UTF-8 BOM つき | 「bad header」で拒否 | 可（MMD も読めない） |
| pmm: 空、magic だけ、ヘッダ直後で切れる | PmmFormatError（位置つき） | 良い |
| pmm: 件数欄を -1 / 2^31-1 に書き換え | 「implausible element count」で即座に拒否 | 良い |

### 3.1 vmd: 書けない名前・値の例外が生のまま利用者に届く

場所: formats/vmd.py:99-103 `_fixed`、123 / 126 の `struct.pack`。

何が起きるか: `mmd bone set ♥ --rot 0 0 1` のように cp932 に無い文字を含む名前は `UnicodeEncodeError`
（type "UnicodeEncodeError"、message は codec の文言）として JSON に出る。負のフレーム（`BoneKey.frame < 0`）は
`struct.error`。どちらも終了コード 1 にはなるが、何が悪いか読み取りにくい。CLI の経路では `--frame` の負値は
`set_frame` が先に弾くので、実際に届くのは名前の件だけ。

直し方: `_fixed` / `_truncated` で `UnicodeEncodeError` を捕まえて `ValueError("bone name %r has characters outside cp932")`
にする。`app.set_bone` の入口で名前を `encode("cp932")` して先に弾いてもよい。

重要度: 低。

### 3.2 vmd: pmm から読んだモデル名を vmd に書き戻せないことがある

場所: app.py:678, 708, 727（`vmd.Motion(model_name=raw["name"] ...)`）、formats/vmd.py:106-110 `_truncated`、
formats/pmm.py:58-59 `pstring`（'replace' で復号）。

何が起きるか: pmm のモデル名に cp932 として壊れたバイト列があると（MMD が名前を途中で切ったときなど）U+FFFD に
置き換えて読み、`set_bone` / `set_morph` / `pose load --register` が vmd を書くときに `UnicodeEncodeError` で落ちる。
モデル名は「モーションデータ読込」の確認を出さないために入れているだけで、確認は自動応答するので厳密に一致する必要は無い。

直し方: `_truncated` の encode を `errors="replace"` にする。

重要度: 低（起きる条件が稀）。

### 3.3 vpd: 親ファイル名の取り出しが "Bone" という文字列で区切っている

場所: formats/vpd.py:35-37。

何が起きるか: `head = body.split("Bone", 1)[0]` なので、親ファイル名に "Bone" を含む vpd（例 `MyBone.osm;`）では
`model_file` が空になる（実測）。`mmd file info` の表示だけに影響し、ボーンの読み取りは正しい。

直し方: `re.split(r"^Bone\d+\{", body, 1, re.M)` のように行頭のブロック見出しで区切る。

重要度: 低。

### 3.4 vmd: `motion load` が種類と件数を知るためだけに全体を解析する

場所: app.py:615（`motion = vmd.load(path)`）、formats/vmd.py:166-208。

何が起きるか: 20 万キー・22 MB で約 1 秒、オブジェクトが数百 MB 分できる。長いダンスモーション（数十 MB）では
`motion load` のたびに秒単位の前処理と大きなメモリを使う。正しさの問題ではない。

直し方: 先頭 50 バイトと各節の件数だけを読む軽い関数（`vmd.peek(path)`）を作り、`load_motion` と `file info` の
`counts` はそれを使う。

重要度: 低。

### 3.5 非有限の数値（nan / inf）がそのまま MMD に渡る

場所: cli.py の `type=float` の引数すべて（`--pos`, `--rot`, `--quat`, `morph set` の値、`--distance` など）、
app.py:74-76 `_format`、mathutil.py。

何が起きるか: argparse の `float` は "nan" / "inf" を受け付ける。`_format(nan)` は 'nan'、`ui_to_quat(nan, 0, 0)` は
全要素 nan の四元数になり、vmd にはそのまま書ける（実測）。MMD の入力欄に "nan" を入れた結果、vmd の NaN を
読んだ結果は確かめていない（推測: 入力欄は 0 扱い、vmd の NaN はポーズが壊れる）。

直し方: `_vector` の cast と `morph set` の値で `math.isfinite` を検査して usage error（終了コード 2）にする。

重要度: 低。

### 3.6 pmm（見たが問題なし、未確認の領域）

- 件数の上限 `_MAX_COUNT`（pmm.py:13, 52-56）と `take` の範囲検査で、壊れたファイルは位置つきの例外で止まる（実測）。
- `_assign_owners`（pmm.py:165-185）は `pre` の連鎖が初期フレームに届かないキーに owner None を付け、scene.py は
  それを `bone: null` として出す。落ちない。
- 末尾に 1 バイトでも残ると「layout was misread」で全体を拒否する（pmm.py:314-316）。試験の fixture はモデル 1 体・
  アクセサリ 1 個・外部親なし・自己影キーなしの場面で、複数モデル、複数アクセサリ、外部親（outside parent）を使った
  場面、重力やセルフシャドウのキーがある場面、MME 入りの MMD が書いた pmm では読み切れるかを確かめていない。
  spike は同梱見本（版 0001）以外の実データを 1 種しか見ていない。実機試験 `test_a_project_that_ships_with_mmd_opens_and_dumps`
  が一番小さい見本だけを開くので、ここは「未確認」として残る。
- `selected_model_index` は u8 で、255 のときは `selected < len(models)` で None になる（scene.py:131）。良い。

## 4. CLI の挙動

### 4.1 `mmd save 別のファイル` が、手で開いたプロジェクトの元ファイルを先に上書きする

場所: app.py:555-572 `save`、526-540 `_save_project`。

何が起きるか: 利用者が MMD で手動で `C:\user.pmm` を開いている（mmd-cli の写しではない）とき、`mmd save D:\copy.pmm` は
`_save_project(allow_foreign=True)` に入り、`record` が無いので第 2 の分岐（`allow_foreign`）で `Menu.SAVE` を送る。
これは `C:\user.pmm` への上書き保存である。そのあと `_save_as(D:\copy.pmm)` で写しを作る。利用者は別のファイルへ
保存するよう指示しただけで `--in-place` も付けていないのに、元のファイルが黙って書き換わる。README の
「mmd-cli を通さずに開かれたプロジェクトでは、保存を伴うコマンドは拒否する。--in-place を付けるとそのファイルへ保存する」
と矛盾する。

根拠: コードの読み取り（分岐を上から追った）。

直し方: `save(path)` で `path` が与えられ、それが現在のパスと違うときは `_save_project` を経ずに直接
`_save_as(path)` する。`path` 無しのときだけ `allow_foreign`（= 利用者が明示した上書き）とみなす。

重要度: 高（利用者のファイルを指示なしに書き換える）。

### 4.2 書き出し先の既存ファイルを MMD が書く前に消す

場所: app.py:519-524 `_save_as`、742-753 `_save_through_menu`（`motion save` / `pose save`）、
916-923 / 931-941（`render image` / `render avi`）。

何が起きるか: 上書き確認ダイアログを避けるために、先に `os.remove(path)` してから MMD に書かせる。MMD が書けなかった
場合（ダイアログで止まる、タイムアウト、ディスクの問題）に、元のファイルは既に無い。`mmd motion save C:\work\dance.vmd`
のように利用者の既存ファイルへ上書きする操作で、失敗時に前の内容を失う。画像・AVI は作り直せるので許容できるが、
pmm / vmd / vpd は利用者の成果物であることが多い。

直し方: 同じフォルダの一時名（`dance.vmd.mmdcli-tmp`）に書かせてから `os.replace` で差し替える。
上書き確認が出る経路（既存ファイルへの保存）は、この方法なら発生しない。

重要度: 中。

### 4.3 ファイルダイアログを通る操作の "message" ハンドラ

場所（b12da4ff 版）: app.py:734-740 `_press_yes`、749 と 790-791。
場所（628a6f8d 版）: app.py:274-288 `_file_handlers.on_message`。`_save_as`（538）、`open_project`（608）、
`_save_through_menu`（765）、`render_codecs`（813）、`render_image`（948）、`render_avi`（998）がこれを使う。

b12da4ff 版の問題: `_press_yes` はどんなメッセージにも はい / OK を押していた。MMD が異常を知らせるメッセージ
（保存に失敗した、など）を黙って閉じ、`done` が満たされず 120 秒後に `OperationTimeout` になり、押した事実は
1.12 のとおり報告されなかった。

628a6f8d 版での変化: `on_message` はメッセージ本文を読み、ボタン（1、2、6 の順）を押し、所有者の窓（ファイル
ダイアログ）に IDCANCEL を投函してから `MmdError("the file dialog refused <path>: <本文>")` を投げる。
黙って待つことは無くなり、本文が利用者に届く。改善である。残る点:

- "message" 種のダイアログをすべて「ファイルダイアログが名前を拒んだ」と解釈する。`open_project` では、pmm を
  開いた後に MMD が出すメッセージ（モデルファイルが見つからない等。推測）も同じ経路に入り、`open_project` は
  失敗として返るが MMD 側はプロジェクトを開き終えている。`_set_record` が呼ばれないので、次の `dump` は
  「mmd-cli を通さずに開かれた」として拒否する。所有者が開いたままのファイルダイアログ（`#32770` で
  `file_name_edit()` を持つ）のときだけ「拒んだ」とし、それ以外は本文つきの `DialogPending` にすると区別できる。
- ハンドラの中から `MmdError` を投げるので、`Mmd._run` は `events` を保存せず（`DialogPending` だけを捕まえる）、
  押したボタンの記録が `answered_dialogs` に残らない（1.10、1.12 と同根）。
- `_press_yes` は死んだコードとして残っている。

重要度: 中（b12da4ff 版）→ 低（628a6f8d 版、上の残件のみ）。

### 4.4 終了コードの境界（低）

- 値の誤り（`frame set -1`、`render size 3`、`render avi --from 5 --to 3`、`play --from 1`（--to なし））は `ValueError`
  で終了コード 1。README の表では 2 が「引数の誤り」。batch の中では同じ誤りが `UsageError` 相当にならず 1 になる。
  `ValueError` を 2 に写すか、これらの検査を argparse 側（`type=` 関数）へ移すと一貫する。
- `MMD_CLI_PID` に数字以外が入っていると `int()` の `ValueError`（"invalid literal"）で 1。環境変数名を含む
  文言にするとよい（app.py:165-166）。

### 4.5 `parse_target` の数字判定（低）

場所: cli.py:13-19。実測: 全角の "１" は `str.isdigit()` が真で `int("１")` も 1 になるので、"１" という名前の
モデルは番号 1 として扱われる。"-1" と "" は名前として扱われる。`text.isascii() and text.isdigit()` にすると
全角は名前になる。

### 4.6 JSON の形（低）

- batch の中で `launch` 行を実行すると、`foreground_restored` に外側の盾の `events` リストそのもの（同じオブジェクト）が
  入る（cli.py:297-298、`dispatch_any`）。その後に起きた出来事が、前の行の結果にも後から現れる。`list(shield.events)` と
  写しを入れる。
- `mmd file info X.pmm` は `scene.summarize(keys=True)` で全キーを出すが、`mmd dump` は既定で `keys=False`。
  同じ場面の表示なので揃えるか、`file info --keys` を設ける。
- `failure()` の `dialogs` には `hwnd` が入る。利用者向けには良いが、`DialogPending` の `events` は出ない（1.12）。

### 4.7 `--out`（見たが問題なし）

- `.part` に書いてから `os.replace`（cli.py:27-31）。相対パスは呼び出し元の cwd 基準で、relay の子も同じ cwd に
  移ってから走る（relay.py:226-227）ので食い違わない。中継の結果は親が利用者の `--out` に書き直す。
- 標準出力は `ensure_ascii=True`（cp932 の端末で壊れない）。pythonw では `stream is None` を見る。良い。

### 4.8 relay の自動判定（1.6 / 1.7 参照）

`--out r.json file info x.pmm`、`--timeout 9 file info x.pmm` を SSH から打つと中継になる（実測で should_relay が True）。
`--out=r.json` の形は正しく判定される。判定を解析済みのコマンド名で行えば直る。

### 4.9 batch（見たが問題なし）

- 行の分割（`split_args`）: 二重引用符でまとめる、バックスラッシュはそのまま、タブも区切り。空白を含むパスは引用符が
  要る（docstring のとおり）。`"a""b"` は `ab`。JSON 行は配列と `{"id", "args"}` だけ。行頭 `[` のパスは
  JSON として読まれ、失敗すれば行番号つきのエラー（実測で `model load [x].pmx` は JSON にならず普通の行として通った。
  `json.loads` が失敗したときの扱い: `line[0] in "[{"` で JSON とみなしてエラーにするので、`[x].pmx` を先頭に置いた
  行は BatchSyntaxError になる。先頭が `[` になる命令は無いので実害なし）。
- 共通オプションを行に書くと BatchSyntaxError（`--pid`、`--out=`）。良い。
- `quit` の行のあとに続く行は「the MMD window is gone」で止まる（既定）か、`--keep-going` で続く。`launch` 行が
  新しいインスタンスを渡す。良い。
- 使い方の誤りは行ごとに `UsageError`（終了コード 2）で報告され、他は `cli.failure` に流す。`DialogPending` の行で
  止まる（3）。良い。

## 6. 見たが問題なしの領域（まとめ）

- ctypes の構造体（INPUT、MOUSEINPUT、KEYBDINPUT、STARTUPINFOW、PROCESS_INFORMATION、DROPFILES）の大きさと配置。
- WM_DROPFILES の HDROP の所有権（投函時にシステムが取る。送り手で解放しない現状が正しい）。
- ハンドルの後始末（CreateProcess、OpenProcess、timeBeginPeriod）。
- FocusShield / timer_resolution の例外時の後始末、入れ子の扱い。
- WM_GETTEXT / WM_SETTEXT / CB_* / LB_* の別プロセス越しの使い方、CB_SETCURSEL 後の通知、BM_CLICK の投函。
- vmd / vpd / pmm の空・短い・壊れた・巨大な件数の入力（上の表）。
- `--out` の原子的な書き出し、ASCII の標準出力、pythonw での出力無し。
- batch の行の分割と共通オプションの拒否、行ごとの終了コード。
- mathutil の変換（既存試験が Z→X→Y の順と UI の符号を独立に検算している）。

## 7. 重要度 高 の要約

- relay: 親は 180 秒、子は `60 + 2 × フレーム数` 秒で待つため、中継経由の `render avi` は 60 フレーム超で必ず失敗し、
  子は消されたファイルを後から作り直す（1.5）。親の待ち時間を子の規則に合わせるか、子の PID が生きている間は待つ。
- `mmd save 別ファイル` は、手で開いたプロジェクトの元ファイルを `--in-place` なしで先に上書きする（4.1）。
  パス指定ありのときは `_save_as` へ直行させる。
