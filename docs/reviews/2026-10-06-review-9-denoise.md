### 3. 網目の測り方と意味（`g3_grid.py`、図 4）

- 測り方: 作業者の `h03b_grid.py` は `mathutil.quat_to_ui`（MMD の窓の角度欄。回転順は Y・X・Z、Y と Z の符号を反転）で、許容 0.02 度。
  自分のベクトル化した換算は `mathutil.quat_to_ui` と 504 キーで差 0、`ui_to_quat(quat_to_ui(q))` の往復は 4e-14 度。換算は正しい。
- 再現: dance_original.vmd の体（指以外・3 キー以上・定数でない軌跡）の角度 74,022 個で 6 度の倍数 89.13%（記録の 89.1% と一致）。
  ただし 0 を除くと 78.4%（4.a）。密なキーだけでも 0 を除いて 79.8%。指は 3.1%（3）。
- 意味: キーは各角度 ±3 度・位置 ±0.15 の量子化を含みうる。既定の上限 3 度は網目の半分で、動かしたキーの 96.4%（6,713 中 6,468）は
  どの角度欄も 3 度以内に収まる（升を出ない）。出る 245 の内訳は 手捩 132・足ＩＫ 78・ひじ 16 など（角度欄の X が 60 度以上のものは 42）。
  回転が大きい所や X が ±90 度に近い所では、角度欄は少しの回転で大きく振れる（回転そのものはどれも 3 度以内）。記録の「X が 0 付近なら升に残る」は、
  キーごとに測ると 3.6% で成り立たない。
- 上限 6 度・0.3 でも、硬い保証（止まり・床・疎なキー・作者の区間・上限）は全部成り立つ（`g1_guarantees.py dn6`）。崩れるのは「トレースと矛盾しない」
  という根拠で、動かしたキーの 22.7%（1,540 / 6,773）が升を出る。下の「上限の推奨」。

### 4. 組み立て順（`g4_pipeline.py`）

- 原文 → 腕補正（dance_arms_open6.vmd）→ `smooth_motion --denoise` → main の `tools/fix_twist.py`:
  最終は 20,934,005 バイト・骨のキー 188,581・表情のキー 54（平滑だけの組み立てと同じ数と大きさ）。
  md5 ff291682… は `variants/dance_arms_open6_smooth_dn_twist.vmd` と一致。
- fix_twist の保証: 右と左の 手捩・手首 で 0〜7742 の全フレームにキー、捩り × 手首 の積は入力（--denoise の出力を MMD どおりに読んだもの）と
  最大 5.5e-6 度で一致、捩りの最大 180 度 → 45.0000 度（45 度以下）、他の骨の 157,609 レコードはバイトも並びも同じ。
- --denoise は捩りの骨の回転軸を変えない（全フレームの軸のずれ 0.000 度。四元数の成分を線形に混ぜるので同じ軸の面に残る）。
- `vmd.load` の往復: main と枝の両方の vmd で `dumps(loads(d)) == d`。

## 確かめられなかったこと

- MMD での見た目（MMD は起動していない）。1 フレームの突起やジグザグが 30 / 60 / 240 fps の描画で見えるか。HANDOVER の A/B（60〜70 秒）は絵でほぼ区別できないとある。
- MMD がフレームの間（60・240 fps の中間）を補間するとき回る向き: 格納の符号の並びが平滑だけと同じことだけ確かめた（向きは平滑だけと同じになる）。
- 拍の山が振付の強調か手ぶれかは、正解の動きが無いので区別できない（2 の「拍の山」は量だけ）。
- 他のダンス。網目が 6 度・0.3 でないトレースでは上限の根拠が変わる。
- 物理の旗・IK の on/off の MMD での振る舞い（値は平滑だけと同じバイトのまま）。
- 試験は worktree そのものではなく、同じコミット（52b45e3、worktree はきれい）を `git archive` した写しで走らせた（worktree に `__pycache__` を書かないため）。
- 記録の 22 変異（`h13_mutants.py`）は走らせていない。自分の 14 変異で代えた。
- 1 の直しの見本は smooth_motion の試験と実物の計測だけで、全体の査読はしていない。2 の直し（小さい区切りを直さない）は出力を後から戻す模擬で、道具には入れていない。
