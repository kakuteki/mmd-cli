## 1. `Mmd._parked` と `Guard.run(keep_hidden=...)`

仕組みの確認: 非表示のインスタンスでは、最外の `_run` が `window_rect` を控えて `move_offscreen`（x = -28000）し、
`Guard.run` は毎周回 `is_visible(main)` を見て、MMD が表示したら `ShowWindowAsync(SW_HIDE)` を 1 回だけ投げる
（`keep_hidden = False` で止めるので連打にならない）。`_parked` の出口で、まだ表示中なら隠し直して最大 5 秒待ち、
最後に `move_window` で元の位置へ戻す。入れ子（`_parking is not None`）は外側に任せる。
現在のコードで `_run` が入れ子になる経路は無い（ハンドラも `done` も `_run` を呼ばない）が、将来の入れ子にも正しく振る舞う。

### 1.1 途中で殺された `mmd` が窓を画面外に残し、以後 `window show` しても見えない窓になる

場所: app.py:304-327 `_parked`、relay.py:245-248（親の `finally` の `schtasks /End`）、app.py:1404-1409 `show`。

何が起きるか: `_parked` は `finally` で戻すので、Python の例外・Ctrl-C では戻る。戻らないのはプロセスごと死ぬとき:
(a) SSH 側の親が Ctrl-C されると `finally` が `schtasks /End` で子（pythonw）を**即死**させる（AVI の途中なら数分間ずっと
この窓）、(b) `taskkill`、(c) `mmd` 自身のクラッシュ。このとき非表示の主窓は x = -28000 に置かれたまま残る。
次の `mmd` は `_parked` の入口で `window_rect` = (-28000, 200) を「元の位置」として控え、終わると**そこへ戻す**ので、
以後ずっと -28000 のまま。`window show`（`SW_SHOWMINNOACTIVE`）は最小化で出すので一見正常だが、人が復元すると
画面外に復元される（下の実測）。2 つの `mmd` プロセスが同じ MMD を同時に動かした場合も同じ（後から入った方が
-28000 を元の位置として控える。README は同時実行を禁じているが、`state` / `window status` 以外の読み出し系
（`bone get`、`camera get` ほか）も `_run` を通るので、人は読み出しなら同時に打つ）。

根拠（実測、`exp_window_place.py`）: 自前の非表示トップレベル窓（表示せず、タスクバーにも出さない）で
`move_offscreen` → `GetWindowPlacement.rcNormalPosition` が (120,130) から (-28000,200) に変わる。
その状態で「2 つ目のプロセス」が `window_rect` を控えて戻しても (-28000,200) のまま。画面内へ `move_window` すれば
rcNormalPosition も戻る。つまり「どこへ戻すか」を窓の現在位置だけから決めると、一度でも退避中に途切れた窓は永久に戻らない。

直し方: 元の位置を窓から読むのではなく、退避前に `state.json` の当該 pid に `home: [x, y]` を書き、戻したら消す。
次の `_parked` は `home` が残っていれば（前回途中で死んだ）それを使う。`show()` は `is_hidden(main)` なら画面内へ
戻してから出す。作業ツリーの未コミット版は「x <= -27900 なら (100,100) に戻す」「`show()` も同じ」で、
主要な経路は塞がる。残るのは、同時実行で先に終わった方が本来の位置へ戻し、後から終わった方が (100,100) に
上書きする順序依存（低）と、`/End` が残す他のもの（2.1、5 節）。

重要度: 中（HEAD。復旧は `mmd quit` → 再起動でできる。作業ツリーで対処中）。

### 1.2 出口で 5 秒待っても隠れないと、表示中の窓を画面内へ戻してしまう

場所: app.py:320-327。

何が起きるか: `is_visible` → `hide`（非同期）→ `_gone(hwnd, 5.0)` が False で戻っても、無条件に `move_window(元の位置)`
するので、MMD が 5 秒以上忙しいまま（大きな出力サイズの AVI 初期化、低速機）だと、**表示中の主窓が画面内に現れる**。
spike の実測は 0.9 秒なので普段は起きないが、「画面に出さない」を守る最後の砦が時間に依存している。
`Guard.run` 側の `hide` が効いていれば出口では既に非表示なので、ここに来るのは `Guard.run` が例外で早く抜けた
（MMD が表示した直後に `DialogPending`）か、MMD が 2 度目に表示した場合に限られる。

直し方: `_gone` が False なら戻さず退避したままにし、`events` に「still visible, left parked」を残す（1.1 の `home` を
書いておけば次回戻せる）。

重要度: 低。

### 1.3 「hidden again」が二重に記録されうる（低）

場所: guard.py:181-186 と app.py:321-326。`Guard.run` が投げた `SW_HIDE` を MMD がまだ処理していない状態で
`Guard.run` が戻ると、`_parked` の出口でも `is_visible` が真で、同じ出来事が 2 件になる。実害は無い。
`_parked` 側は「guard が既に隠した」ことを知らないので、`Guard.run` の戻り値の `events` に `hidden again` が

### 1.4 別プロセスの窓への `SetWindowPos` は相手が固まっていると戻らない（低）

場所: win32.py:394-403 `move_offscreen` / `move_window`。`SetWindowPos` は相手スレッドへ同期で `WM_WINDOWPOSCHANGING`
を送るので、MMD が応答不能だと `_parked` の入口で `mmd` が無期限に止まる（`SendMessageTimeout` と違って期限が無い）。
`Guard.run` の `send` は 5 秒で諦めるのに、その直前の退避で止まる形。`SWP_ASYNCWINDOWPOS`（0x4000）を付ければ
投函になり止まらない（位置が効くまでの数 ms は読み戻せないが、ここでは問題ない）。

### 1.5 `launch` の間は盾の pid が None で、前面を取られても戻さない（低）

場所: cli.py:308-310、guard.py:68。`FocusShield(pid=None)` で起動し、`shield.pid` は `launch` が戻ってから入る。
起動中に MMD が出すメッセージボックス（Direct3D の失敗、MME の警告）が前面を取っても `_check` は `self.pid and ...`
で何もしない。`LockSetForegroundWindow` が掛かっていれば取られないので、権利が無い（端末が前面でない）ときだけの話。
`launch_detached` の直後に pid が分かるので、`launch(exe, on_pid=lambda pid: ...)` のような形で盾に渡せる。

### 1.6 見たが問題なし

- 例外経路: `_parked` は generator ベースの context manager で、`yield` の前に例外を出す呼び出しは無い
  （`is_visible` / `window_rect` / `move_offscreen` は失敗しても例外にならない）。`finally` で `_parking` を None に戻す。
- `quit` の最中: `quit` は `_run` を通らないので `_parked` と無関係。別プロセスの `quit` で窓が消えた場合、
  出口の `is_visible(消えた hwnd)` は偽、`move_window` は黙って失敗する（実測: 破棄した hwnd の `window_rect` は
  (0,0,0,0)、`IsWindow` 偽）。例外にはならない。
- `window show` / `hide` / `minimize` は `_run` を通らず、操作の間に挟まることも無い（1 プロセス内では順次）。
  最小化したまま `hide` した窓（iconic かつ非表示）を `_parked` が退避しても、`SetWindowPos` は最小化中の位置を
  動かすだけで rcNormalPosition は変わらない。
- `window_rect` が (0,0,0,0) を返すのは hwnd が無効なときだけ（実測）。そのときの `move_window(0, 0)` も無害。
- 見える最小化インスタンス（既定起動）では `hidden` が偽で何もしない。
- `_run` の `DialogPending` 以外の例外で `Guard.run` の `events` が落ちる件は 5.2 にまとめた。

## 2. `keeping_the_old_file`

実測は `exp_keep_old.py`（`tests/test_app_behaviour.bare()` に偽の `menu` を差して `_save_as` / `_save_through_menu` を
呼んだ。MMD は使っていない）。

### 2.1 前回の実行が残した `名前.mmdcli-old` を、次の実行が黙って消す

場所: app.py:159-163。

何が起きるか: 途中で死んだ実行（1.1 の `/End`、taskkill、クラッシュ、電源断）は `finally` を通らないので、利用者の元ファイルは
`X.mmdcli-old` に、書きかけが `X` に残る。利用者がもう一度同じ命令を打つと、`os.path.exists(aside)` → `os.remove(aside)` で
**元ファイルの唯一の写しを消してから**、書きかけの `X` を `X.mmdcli-old` に退避する。成功すればそれも消える。
2 手（中断 → 再実行）で元ファイルが無くなる。中継の Ctrl-C が子を即死させる今、現実的な経路である。

根拠: 実測 A3。`dance.vmd.mmdcli-old`（原本）と `dance.vmd`（書きかけ）がある状態で `_save_through_menu` を成功させると、
終了後のフォルダは `['dance.vmd']` だけで原本は消えた。

直し方: `aside` が既にあれば消さずに別名（`X.mmdcli-old.1`, `.2`…）へ退避するか、`MmdError("a previous run left X.mmdcli-old;
move it away first")` で止める。成功時に消すのは自分が今作った退避だけ。

重要度: 高（利用者の成果物が無くなる。発生に 2 手要るが、どちらも普通の操作）。

### 2.2 書き出し先が既存のディレクトリだと、そのディレクトリが `名前.mmdcli-old` に改名される

場所: app.py:150-151 `check_output_file`、app.py:159-163。

何が起きるか: `check_output_file` はディレクトリを弾かない。`mmd save C:\work`（ファイル名を書き忘れた）や、
`shots.png` という名のフォルダがある所への `render image` では、`os.replace(dir, dir + ".mmdcli-old")` で**利用者のフォルダが
改名され**、MMD はその名で（拡張子を補って、推測）保存しようとする。MMD が `C:\work` そのものに書かなければ `_not_written` の
例外経路で `os.replace(aside, path)` が走って改名は戻る（推測。実機未確認）。偽の MMD が `path` に書いた実測では、成功経路の
`os.remove(aside)` が `PermissionError`（WinError 5。ディレクトリは `remove` できない）になり、フォルダは改名されたまま、
中身は無事、命令は「アクセスが拒否されました」で失敗した。

根拠: 実測 A1、A6（`os.replace` はディレクトリも改名でき、`os.remove` は WinError 5）。

直し方: `check_output_file` で `os.path.isdir(path)` なら `MmdError("%s is a folder: give a file name")`。
`keeping_the_old_file` も `os.path.isfile(path)` のときだけ退避する。

重要度: 中（データは残るが、利用者のフォルダ名が変わり、原因の分からないエラーになる）。

### 2.3 既存ファイルが読み取り専用だと、MMD が書いた後に `PermissionError` で失敗扱いになる

場所: app.py:172-176（成功経路の `os.remove(aside)`）、167-170（失敗経路の `os.remove(path)`）。

何が起きるか: 読み取り専用のファイルは改名できる（退避は通る）が消せない。MMD が新しいファイルを書き終えた後の
`os.remove(aside)` が `PermissionError` を投げ、**成功した書き出しが失敗として報告され**、`X.mmdcli-old` が残る。
失敗経路で書きかけが読み取り専用だった場合（稀）は `os.remove(path)` の例外が本来の例外を覆い隠す。

根拠: 実測 A2（`dance.vmd` を S_IREAD にして成功させると、戻り値の代わりに WinError 5。`dance.vmd` の中身は `new`、
`dance.vmd.mmdcli-old` が残る）。

直し方: 退避・削除の前に `os.chmod(…, S_IWRITE)`、または後始末の失敗は `try/except OSError` で捕まえ、成功は成功として返しつつ
`"old_copy": aside` のように残した場所を結果に添える。

重要度: 低〜中（Git 管理のファイルや配布物を読み取り専用にしている人はいる）。

### 2.4 `render_avi` は検査に外れると**新しい AVI を消して古い方を戻す**

場所: app.py:1207-1218（`with keeping_the_old_file(path)` の中で `_avi_info` → `MmdError`）。

何が起きるか: `keeping_the_old_file` の例外経路は「MMD が書き終えなかった」ことを想定して `os.remove(path)` する。しかし
`render_avi` はその中で成果物の検査もしているので、検査に外れた時点で、数分〜数十分かけて書いた AVI が**消える**。
外れる条件は (a) 本当に頼みと違った（`--size` が効かない版の MMD。今日の記録にある「640x360 の指定が効かず 1280x720 で出来た」が
この版なら、その 1280x720 の AVI は消えていた）、(b) 検査側の誤り: e12cc25 版は先頭 4096 バイトしか読まず `dmlh` も見ないので
1 GB 超の AVI（非圧縮 1280x720 なら約 12 秒ぶん）は必ず枚数不一致になった（827de16 で修正済み）。HEAD でも `_avi_info` が
`{}` を返せば（6.1）3 項目すべて不一致になり消える。(c) 推測: `_written` は「大きさが 0.2 秒変わらない」で完了を決めるが、
avifil32 はクローズ時に `avih` / `dmlh` の枚数を**同じ場所へ上書き**する（大きさは変わらない）。その上書きの前に
`_avi_info` が読むと枚数が 0 や途中値になりうる。窓は小さいが、はずれたときの罰が「成果物の削除」なのが釣り合わない。
同じ `with` の中の `if problem: raise`（コーデック不一致でキャンセル）は何も書かれていないので問題ない。

根拠: コードの読み取りと実測 A4（`with` の中で書いた後に `MmdError` を投げると、新しい方が消え古い方が戻る）、
D4（`_avi_info` が `{}` のとき `wrong` が 3 項目になる）。

直し方: 検査は `with` の外へ出す（新しい AVI は残し、元ファイルは既に退避済みなので失われない）。検査に外れたら消さずに
`X.mmdcli-unverified.avi` のような名前に改名して、エラー文にその場所と読めたヘッダを入れる。完了判定は大きさだけでなく
`RecWindow`（録画中(N frame)）が消えたことも使う（`recording` ハンドラでその hwnd を控え、`done` で `is_window` が偽になるのを待つ）。

重要度: 中（HEAD。e12cc25 では高）。

## 3. `_state_lock` / `update_state` / `save_state`

### 3.1 錠なしの「読む → 変える → 書く」が 2 か所残っている

場所: app.py:1433-1437 `Mmd.quit`（`load_state()` → `projects.pop` / `current = None` → `save_state`）、
tests/live/test_live.py:687-689 `test_minimized_instance`（`current` を戻す）。

何が起きるか: `quit` と別インスタンスの `launch` / `_set_record` が重なると、古い状態の書き戻しで相手の `current` や
`projects` の項目が消える（査読 1 の 1.9 と同じ事故）。`quit` は 2 体目を閉じながら 1 体目を操作する、という場面で普通に重なる。
`save_state` 自体の原子性（pid+スレッド id 付き tmp、`os.replace` の再試行）は保たれているので、壊れた JSON にはならない。

直し方: `quit` は `update_state(lambda s: (s["projects"].pop(str(pid), None), s.__setitem__("current", None) if s.get("current") == pid else None))`
に。実機試験も `app.update_state` を使う。

重要度: 中。

### 3.2 10 秒で古い錠を消す規則は、持ち主が生きている限り発動しない（実測。問題なし）

場所: app.py:85-91。

懸念は「遅い持ち主の錠を 10 秒で横取りし、持ち主が後から横取りした側の錠を消す」競合だった。実測（`exp_state_lock.py` B1）:
持ち主 A が錠の mtime を 15 秒前に書き換えて 1 秒握り、0.2 秒後に B が来ても B は A が離すまで待った（B 1.00〜2.50、
C 2.50〜3.00、重なりなし）。理由は B4: 持ち主が fd を開いたままの錠は `os.remove` が `PermissionError`（WinError 32）になり、
`except OSError: pass` で待ちに戻るから。`_state_lock` は `with` の間ずっと fd を開いているので、横取りできるのは持ち主の
プロセスが死んで fd が閉じたときだけ。これは意図どおりである。`os.close(fd)` と `os.remove(lock)` の間の数 µs は錠が新しいので
10 秒規則に掛からない。

付随して測ったこと: `update_state` の所要時間は中央値 15 ms、最大 31 ms（死んだ pid 10 件を `process_alive` で濾した状態）。
10 秒の閾値に対して十分小さい。

残る点（低）: 錠が別の理由で消せない（権限、ロックが実はディレクトリ）ときも 5 秒後に「the state file is locked by another
mmd command」と言う（実測 B2: 5.0 秒で同じ文言）。`errno` を添えると切り分けが早い。

### 3.3 その他（低）

- `_record()` / `attach` の読み出しは錠なしだが、`os.replace` が原子的なので読み手は常に完全な JSON を見る。書き手側が

  照合するので実害なし。

## 4. `app.launch` の起動時ダイアログ

### 4.1 同じダイアログを 100 ms ごとに押し直し、記録も重複する

場所: app.py:199-211。

何が起きるか: `guard.click` は `WM_COMMAND` を**投函**するだけで、閉じるのを待たずに次の周回へ進む。MMD が初期化で忙しくて
100 ms 以内に閉じなければ、次の周回で同じ hwnd にもう一度 OK を投函し、`said` にも同じ本文がもう 1 件入る。
`mmd.events`（結果の `answered_dialogs`）に同じ通知が 2〜3 件並ぶ。閉じかけのダイアログへの 2 回目の投函は無害だが、
その hwnd が 100 ms 以内に**別の**ダイアログに再利用されていれば、読まずに押したことになる（稀）。

根拠: 実測（`exp_launch_guard.py` E。偽の `open_dialogs` が同じ通知を 3 周回返すと、投函 3 回、`events` 3 件）。
`tests/test_app_behaviour.LaunchFailureTest` は `dialog_rounds.pop(0)` で 1 周回しか見せないので、この形は試験に現れない。

直し方: `guard.quit` と同じく押した hwnd を `answered` に控え、同じ hwnd には押さない。`said` も hwnd で重複を除く。

重要度: 低（記録が汚れる。押し直し自体は無害）。

### 4.2 90 秒の時間切れでは、隠したダイアログを持った MMD が生きたまま残る

場所: app.py:220-221。

何が起きるか: 1.14 の対処は「答えられない質問 → 終了」「通知 → OK」の 2 経路だけで、`OperationTimeout` の経路は
プロセスを終了しない。`open_dialogs(hide=True)` が透明化・画面外へ置いたダイアログは、OK を押しても閉じないダイアログ
（押下が効かない、同じ通知が出続ける）のまま 90 秒後に残り、主窓が無ければ `attach` できず `dialog show` も効かない。
査読 1 の 1.14 が指摘した詰み方がこの経路にだけ残っている。`said` の文言も `OperationTimeout` の文には入らない。

直し方: 時間切れでも `open_dialogs(pid, main)` が空でなければ `reveal_window` で見せるか `terminate_process` し、
文言と pid を例外文に入れる（`MMD exited right after …` の文と同じ形）。

重要度: 中（起きるのは環境依存の起動失敗だけだが、起きたときに手が出ない）。

### 4.3 OK/キャンセルの 2 択は「質問」なのに OK を押す

場所: app.py:205-206。

何が起きるか: 判定は「6（はい）があれば質問、1 か 2 があれば通知」。OK と キャンセル の両方を持つダイアログは、
MessageBox でいえば `MB_OKCANCEL` の質問（「〜しますか？」）だが、OK が押される。MME の警告のような OK だけの通知と、
OK で何かを**承諾する**ダイアログの区別はボタンの数でしかつけられない。また、2（キャンセル）しか無いダイアログを
押したときも `action="ok"` と記録される。

直し方: ボタンが 1 つなら押す、2 つ以上なら答えられない（終了）に寄せる。記録の `action` は押したボタンの文言にする。
起動時に OK/キャンセル を出す場面は v9.32 では知られていないので、現状の実害は無い（推測）。

重要度: 低。

### 4.4 100 ms 間隔の見張りでは起動時ダイアログが一瞬画面に出る（低）

場所: app.py:222 `time.sleep(0.1)`。`Guard.run` は 1 ms 間隔で「表示される前」に捕まえる設計だが、`launch` は 100 ms 間隔なので
起動時の通知は最大 100 ms 画面中央に不透明で出てから透明化される。`FocusWatch` も起動の後に始まるので実機試験では見えない。
`with win32.timer_resolution():` の下で 5 ms 程度にすると揃う。

### 4.5 見たが問題なし

- 終了経路（`terminate_process`）では隠したダイアログも一緒に消えるので、見せ直す必要は無い。
- `MMD exited right after it was started` の経路も同様。`said` を文に添えている。
- `mmd.events.extend(said)` で起動時の通知が最初の結果に載る。`LaunchFailureTest` の 3 本が守っている。

## 5. ファイルダイアログ（`_file_handlers` / `_fill_file_dialog`）と滞留規則

### 5.1 遅いドライブで「正しい名前」を拒否と誤判定しうる（推測）

場所: guard.py:16 `LINGER_SECONDS = 2.0`、guard.py:195-202、251-257 `_lingers`、app.py:380-392。

何が起きるか: 拒否の判定は「OK を投函して 2 秒たっても、表示中・有効・`WM_NULL` に 100 ms 以内に答える」。保存ダイアログが
OK の処理（パスの検証、フォルダの列挙）に 2 秒以上かけ、その間メッセージを処理している場合（ネットワークドライブ、
スピンダウンした HDD、ウイルス対策の走査）は、この条件を満たして**キャンセルされ**、「the file dialog refused …」で失敗する。
OK の処理中にダイアログのスレッドが塞がっていれば `WM_NULL` が時間切れになって救われるが、新式ダイアログは COM の
非同期処理で UI スレッドを塞がないことが多い（推測。実測はローカルディスクのみ）。

直し方: 時間だけで決めず、spike が実測した拒否の署名「入力欄が空に戻る」を使う。2 秒たっても開いているとき
`get_text(edit) == ""`（または path と違う）なら拒否、まだ path が入っていれば処理中とみなして `LINGER` を延ばす
（上限は操作の `timeout`）。`_fill_file_dialog` の 2 回目の呼び出しでこの判定ができる。

重要度: 中（hinata の運用先がローカルディスクなら今は当たらない。推測であることを明記）。

### 5.2 失敗したときに、押したボタンの記録と通知の文言が落ちる経路が残っている

場所: app.py:293-301 `_run`（`DialogPending` だけ `events` を拾う）、guard.py:243-247（`OperationTimeout` に `events` を
載せない）、app.py:964-971 / 731-736 / 1151-1159 / 1164-1219（`OperationTimeout` に `said` を添えない）。

何が起きるか: `Guard.run` が集めた `events`（「file name entered」「settings entered」「recording」、通知の「ok」とその本文）は、
ハンドラが `MmdError` を投げたとき（`_file_handlers.on_message` の拒否、`_fill_file_dialog` の 2 回目）と、期限切れの
`OperationTimeout` のときに**捨てられる**。`cli.run` が付ける `exc.answered_dialogs` は `mmd.take_events()`、すなわち
それまでの `_run` と `_parked` の分だけ。README の「失敗した場合も、そこまでに自動で押したボタンは error.answered_dialogs に残る」
「MMD 自身が出す通知は閉じて文言を控え、続く失敗の文に添える」は、`_not_written` と `open_project` の時間切れでは守られ、
`motion save` / `render image` / `render avi` の時間切れでは守られない。例: 保存中に MMD が「保存に失敗しました」（OK のみ、
所有者は主窓）を出すと、`on_message` が OK を押して `said` に入れ、ファイルが現れないまま 120 秒後に
「MMD did not finish within 120 s」だけが返る。

根拠: 実測（`exp_launch_guard.py` F。偽の win32 で通知 A を "ok" で処理した後、通知 B のハンドラが `MmdError` を投げると、
例外に `events` は無く、`cli.failure` の `error` は `type` と `message` だけ）。

直し方: `Guard.run` は例外を投げる前に `exc.events = events` を付ける（`DialogPending` と同じ扱いに統一）。`_run` は
`except Exception as exc: self._keep(getattr(exc, "events", []))`。`OperationTimeout` を投げる所では `said` も添える
（`open_project` と同じ形を `_save_through_menu` / `_save_as` / `render_*` に）。

重要度: 中（README の約束と違う。原因究明に一番要る情報が落ちる）。

### 5.3 二重キャンセルと `_gone` の上限（見たが問題なし）

- 滞留経路（`_fill_file_dialog` 2 回目）とメッセージ経路（`on_message`）は排他: メッセージが上に乗ると親は無効になり
  `_lingers` が偽になる。メッセージが OK の 2 秒以上後に出た場合だけ、先に滞留経路がキャンセルを投函し（無効な親への
  `BM_CLICK` は効かない）、`_gone` が 5 秒で偽 → 「the dialog is still open」付きの `MmdError`。残った 2 枚は次の命令で
  `DialogPending` になり `dialog show` で見える。詰まない。
- `_gone` の上限は 3 秒 + 5 秒（`on_message`）、5 秒（`_fill_file_dialog`）。合計 8 秒で必ず戻る。
- `is_enabled` + `WM_NULL` の組は、「モデル情報」のように OK 後も処理しながら開いたままのダイアログを一般規則から外す
  目的（`kinds[hwnd] == "file_dialog"` 限定）で足りている。
- `said` の届き方: 成功時は `events` 経由で `answered_dialogs` に本文つきで載る。失敗時は 5.2 のとおり。

## 6. `render_avi` の検査（`_avi_info`）と出力サイズ

### 6.1 実測した MMD の AVI のヘッダ配置と、読み取り窓の余裕

実測（`exp_avi.py` D1、`_spike/out/verify/clip.avi` ほか 4 本、MJPEG と非圧縮）: `avih` は常に offset 24。`hdrl` の LIST は
32,492 バイトで、`strl` の中の `indx`（OpenDML のスーパーインデックス）が 32,024 バイトを占める。`LIST odml` / `dmlh` は
offset 32,244 / 32,256 にある。`dwMicroSecPerFrame` は 33333、`dwTotalFrames` と `dmlh` の総枚数は一致（5 / 21 / 31 / 300）。
`strh` の fccHandler は MJPEG で `MJPG`、非圧縮で 0。

- e12cc25 版（先頭 4096 バイト）では `dmlh` は窓の外。827de16 で 65,536 に広げ `dmlh` を優先するようになった（HEAD）。
- 窓の余裕: ストリームが 2 本（音声つき AVI）なら `dmlh` は offset 64,412 で窓の内側（余裕 1,112 バイト。実測 D2:
  `clip.avi` の `strl` を複製して作った 2 本構成で `_avi_info` は `dmlh` の 7743 を返した）。3 本なら 96,568 で窓の外になり、
  `avih` の第 1 区画の枚数へ落ちる（D3）。MMD が 3 本書くことは無いので実害は無いが、固定長の `find` は「読めたつもり」に
  なりやすい。
- `head.find(b"avih")` / `find(b"dmlh")` は RIFF の構造を辿らず最初の一致を取る。`avih` は必ず先頭なので安全。`dmlh` は
  `strf` のコーデック私有データや文字列に同じ 4 バイトが現れれば誤読するが、`hdrl` の中に限れば現実的でない（低）。

直し方（低）: RIFF の chunk を辿る 20 行の関数にして、`hdrl` の長さぶんだけ読む（`12 + 8 + hdrl_len`。実測では 32,512）。
`dmlh` は `LIST odml` の中だけで探す。

### 6.2 `_avi_info` が `{}` を返す条件と、その結果（2.4 の根拠）

`RIFF` でない・`AVI ` でない・`avih` が窓に無い・`avih` の 48 バイトが欠ける、のいずれかで `{}`。このとき `render_avi` の
`wrong` は `frames`, `fps`, `size` の 3 項目とも `(頼んだ値, None)` になり（実測 D4）、2.4 のとおり新しい AVI が消える。
MMD が書いた完全な AVI で `{}` になることは実測の範囲では無いが、2.4 (c) の「ヘッダ確定前に読む」場合は `avih` の枚数が
0 のまま読めてしまう（`{}` ではなく不一致）。どちらにせよ罰が「削除」なのが問題で、検査の正確さを上げるより先に
削除をやめるべき。

### 6.3 fps の丸めと `dwMicroSecPerFrame = 0`（見たが問題なし）

`round(1e6 / µs)`: 33333 / 33334 → 30、41666 / 41667 → 24、16666 / 16667 → 60、40000 → 25（実測 D5）。整数 fps の
往復には十分。29.97（33367 µs）も 30 に丸まるが、`--fps` は `int` なので頼めない値であり、MMD が 29.97 で書くことも無い。
µs = 0 のときは `fps: None` → 「fps asked 30, written None」の不一致になる。壊れたヘッダを不一致として報告するのは妥当。

### 6.4 `set_output_size` の副作用（見たが、文書どおり）

`render avi --size` / `render image --size` は「出力画面サイズ」の設定を書き換え、MMD の設定として起動をまたいで残る
（spike 実測、README 制約に明記）。戻す選択肢（前の値を `output_size()` で読んでおき、終わったら戻す。ダイアログ往復が
2 回増える）はあるが、README の約束と一致している現状を変える必要は無い。`set_output_size` は `keeping_the_old_file` と
`_camera_mode` の**外**で呼ばれているので、サイズ変更が失敗しても出力先には触れない。正しい順序。

### 6.5 小さな点（低）

- app.py:1205 と 1211: `written` が「done 用の関数」から「ヘッダの辞書」に付け替えられる。`done` はその後呼ばれないので
  動くが、読み手が迷う。`header` などに改名する。
- `--timeout` の意味: `cli.py:75-76` のヘルプは「AVI output allows 2 s per frame on top」だが、`render_avi(timeout=args.timeout)`
  は値があればそのまま使い、枚数の上乗せをしない（`if timeout is None:` の中だけ）。README 制約の「足りなければ --timeout」とは
  整合するので、ヘルプの文言を直す。
- `tests/test_avi_header.py` の `test_opendml_total_frames_win_over_the_first_segment_count` は `dmlh` が offset 100 付近にある
  合成ファイルで通る。実機の配置（32,256）と、2 本構成の 64,412 を fixture に加えると窓の境界が試験で守られる（11 節）。

## 7. relay（`relay.py`、`cli.main`）

### 7.1 親が諦めるときの `schtasks /End` は子を即死させ、途中状態を残す

場所: relay.py:245-248、cli.py:547。

何が起きるか: 親が `RelayError`（起動 15 秒・結果なし 2 秒）か **Ctrl-C**（`finally` は `BaseException` でも走る）で抜けると
`/End` が pythonw を `TerminateProcess` 相当で止める。子が `keeping_the_old_file` の中なら 2.1 の状態（原本が `.mmdcli-old`）、
`_parked` の中なら 1.1 の状態（窓が -28000）、ファイルダイアログや AVI 設定ダイアログを開いていれば**透明なダイアログが
開いたまま**の MMD が残る（次の命令で `DialogPending`、`dialog show` で見える）。子が `batch` なら途中の行まで実行済み。
SSH で長い AVI を待っている人が Ctrl-C するのは普通の操作なので、「親の中断 = 子の即死」は重い。

直し方: Ctrl-C では `/End` せず、子を走らせたまま「結果は `relay/<id>.out.json` に残る」と言って戻る（job ファイルは消さない
ので子は結果を書く。1.8 の後始末規則と両立させるには `.abandoned` の印を置く）。あるいは子が周回ごとに `.stop` を見て
`MmdError("stopped by the caller")` で**自分から**抜ける（`Guard.run` のループと `_wait_for` に 1 行ずつ）。`/End` は
子が本当に固まったときの最後の手段に限る。

重要度: 中。

### 7.2 `process_alive` は「開けない」と「死んだ」を区別しない

場所: win32.py:509-516、relay.py:237-242。

何が起きるか: `OpenProcess(SYNCHRONIZE)` が `ERROR_ACCESS_DENIED` でも偽を返す。親から子が開けない環境（別の利用者で
走る sshd、保護プロセス、将来の整合性レベルの変更）では、`.started` の約 2 秒後に「ended without leaving a result」になり、
子は走り続けて結果を書き、1.8 の規則で自分の結果を消す。hinata のセッション 0 から同一利用者の子は開けた（5cb2edc の記録、n=1）
ので今の運用では当たらない。

根拠: 実測 G。この PC の `services.exe`（SYSTEM、セッション 0）に対して `process_alive` は偽、直後の `GetLastError` は 5。
自分の pid は真、存在しない pid は偽。

直し方: `process_alive` が `OpenProcess` に失敗したら `GetLastError` を見て、5（access denied）なら「不明」を返し、
親は不明のときは `.exit` の出現だけを待つ（`schtasks /Query /TN name /FO CSV` の「実行中」でも代用できる）。
`win32.send` と同じく、失敗の種類を戻り値に残す。

重要度: 低（今の運用では起きない。起きたときの症状は分かりにくい）。

### 7.3 その他（低）

- PID の再利用: 子が `.exit` を書かずに死に、2 秒以内に同じ PID が別のプロセスに割り当てられると、親はそのプロセスが
  終わるまで待つ。Windows は PID をすぐ再利用するが、2 秒以内は稀。`.started` に PID と**開始時刻**（`GetProcessTimes` の
  作成時刻）を書いて照合すれば塞がる。
- `.part` の残骸: `_write_whole` と `emit` の `.part` は、書いている最中に子が止まる（7.1）と残る。親の後始末の一覧
  （relay.py:249）に `*.part` も入れる。
- `collect` の順序: `.exit` は `.out.json` の後に原子的に置かれるので、`.exit` を見てから `.out.json` を読む親は半端な JSON を
  読まない。`run_job` のエラー JSON（relay.py:277-279）は非原子的に書かれるが、`.exit` の前なので同じ理由で安全。
- `run_job` で `main` が `SystemExit` を出すと（usage error）`.out.json` が無いまま `.exit` だけ書かれ、親は「left no result」
  の `RelayError`（終了コード 1、本来は 2）になる。親が同じ argv を先に解析しているので、子で usage error になる経路は
  実質無い。
- `schtasks` の `/End` / `/Delete` は `timeout=60` 付きで、`finally` の中で `TimeoutExpired` を出すと本来の例外を隠す。
  `try/except subprocess.SubprocessError: pass` で包む。
- 子が「生きたまま固まる」場合: 子の待ちはすべて上限つき（`Guard.run` の timeout、`_wait_for`、`_gone`、`send` 5 秒、
  `_state_lock` 5 秒、`schtasks` 60 秒）で、唯一の例外は 1.4 の `SetWindowPos`。親に上限が無いのは子の寿命で待つ設計の帰結で、
  子が自分で抜ける限り問題ない。
- `relay_dir()` は `home_dir()` の cp932 検査を通らない（査読 1 の 1.15 は relay も対象にした）が、relay のファイルは
  Python と schtasks（Unicode）しか読まないので検査は要らない。問題なし。
